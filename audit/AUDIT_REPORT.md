# Полная инспекция проекта

Дата проверки: 12 августа 2026 года.

Проверен весь переданный архив: TypeScript/TSX, расчёт Казахстана и Германии, виртуальные и фактические операции, сохранение Supabase, импорт/экспорт, CSS, SQL-схема, авторизация, документация и служебные файлы.

## Исправлено

### 1. Ошибка production build в `FinanceApp.tsx`

`toggleVirtualPayment()` принимал общий union `VirtualOperation`, хотя внутри без проверки обращался к `item.payment`. Для варианта регулярного дохода поля `payment` не существует, поэтому `next build` падал на проверке типов.

Исправлено: обработчик принимает только `VirtualPaymentOperation`. Вызов уже находится внутри ветки `virtual_kind === "payment"`, поэтому тип теперь соответствует фактической логике.

### 2. Регулярные доходы Казахстана: дневник и прогноз приведены к одной модели

Новая логика отображения регулярных доходов была неполной. Исправлено:

- плановый регулярный доход отображается в дневнике виртуальной строкой;
- при отметке как факт создаётся месячная операция с `source_recurring_income_id` и `source_month`;
- при возврате факта в план месячная операция удаляется, после чего снова появляется актуальная виртуальная строка из настроек;
- поиск уже материализованного дохода выполняется по `source_month`, а не только по фактической дате операции;
- прогноз подавляет плановый доход именно для исходного месяца события (`source_month`), поэтому перенос фактической даты в другой месяц больше не подменяет регулярный доход соседнего месяца;
- фактическая сумма при переносе даты учитывается в месяце фактической даты, а регулярное событие следующего месяца остаётся самостоятельным.

Это устраняет дубли, пропавшие строки и рассинхронизацию дневника с календарным прогнозом.

- Конфликтующие старые переопределения `relocationPanel` и `germanyForecastBox` объединены с действующими правилами.
- Удалены CSS старого большого блока расчёта зарплаты (`salaryGrid`, `salaryResults`, `checkLine`, `smallWarn`) после перехода на компактную строку.

## Что не проверено полноценной production-сборкой в контейнере

В архиве нет `node_modules` и lock-файла. Установка зависимостей в среде проверки не завершилась, поэтому реальный `next build` здесь не используется как доказательство успешной сборки. Внутренняя проверка типов после исправления ошибки `VirtualOperation` проходит чисто; окончательная проверка — следующий Vercel deployment или локальный `npm install && npm run build`.

## Оставшиеся архитектурные ограничения, не являющиеся текущими ошибками

- В проекте нет `package-lock.json`, поэтому разрешённые `^`-версии зависимостей могут обновляться между чистыми установками. Для полностью воспроизводимых сборок стоит закоммитить lock-файл после успешного `npm install` в обычной среде.
- Импорт резервной копии выполняется несколькими клиентскими запросами Supabase и не является одной SQL-транзакцией.
- Автокурс EUR зависит от HTML-разметки внешнего `mig.kz`; при изменении разметки серверный парсер потребует обновления.
