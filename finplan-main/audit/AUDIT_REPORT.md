# Отчёт полной инспекции

Дата проверки: 4 августа 2026 года.

Проверен весь переданный архив: компоненты, расчётная логика, сохранение Supabase, импорт и экспорт, CSS, SQL, настройки авторизации и служебные файлы.

## Исправленные ошибки

### Сохранение и согласованность данных

- Последовательные изменения плана Германии больше не отправляются конкурирующими запросами в произвольном порядке.
- Сохранения из основного экрана Германии и из `Настройки → Германия` координируются, поэтому старая версия JSON не должна перезаписывать более новую.
- При переключении вкладок отложенное сохранение немецких расходов не отбрасывается.
- Перед импортом приложение останавливает отложенные записи Германии и ожидает уже запущенные запросы.
- Импорт теперь действительно заменяет и `relocation_plans`; старый немецкий план не остаётся после импорта файла без этого раздела.
- После импорта открытый компонент Германии получает импортированный план или загружает новый план по умолчанию, вместо повторной записи старого локального состояния.
- Основные настройки, платежи и доходы получают дополнительную принудительную запись перед выходом из аккаунта или размонтированием приложения.

### Расчёты

- Прогноз Германии рассчитывается одним проходом, без двух старых параллельных моделей данных.
- В общий прогноз включены и доходы, и расходы Казахстана. Они выводятся отдельными суммарными строками.
- Немецкие статьи доходов и расходов используют общие названия статей Казахстана.
- Месячные галочки расходов Германии сохраняются как отдельные исключения и учитываются в прогнозе только соответствующего месяца.
- Удалён двойной учёт старых копий регулярных платежей.
- Старые материальные операции регулярных доходов скрыты из чек-листа, но корректно учитываются при миграции старых данных.
- Отрицательные или нечисловые суммы в настройках и плане нормализуются; дни платежей ограничены диапазоном 1–31.
- Повреждённые значения месяца не используются как действительные периоды.
- При редактировании ручной операции сохраняются её галочка и порядок, а не сбрасываются в план.
- Перемещение операции выполняется последовательно; при ошибке второй записи первая откатывается.

### Статьи и периоды

- Переименование статьи синхронизируется со сценариями и регулярными расходами Германии.
- При удалении статьи связанные ручные операции безопасно теряют ссылку, а немецкие группы переводятся в оставшуюся статью.
- Запрещено создавать одинаковые названия статей без учёта регистра.
- Новые статьи получают уникальные временные названия.
- Импорт удаляет повторяющиеся названия статей.
- Если окончание периода раньше начала, окончание очищается.
- Начало регулярного расхода Германии привязано к фактическому началу немецкого сценария, а не к произвольному старому месяцу дневника.

### Интерфейс и CSS

- Удалены накопившиеся старые CSS-блоки карточной версии настроек и прежних вариантов планировщика.
- В итоговом CSS нет повторяющихся верхнеуровневых селекторов и неиспользуемых классов.
- Проверен баланс фигурных скобок CSS.
- Календарь Германии использует полный горизонт, читаемые месячные колонки и горизонтальную прокрутку.
- Статьи доходов и расходов раскрываются отдельными кнопками.

## Что не удалось проверить в контейнере

Полную команду `npm run build` запустить не удалось. В доступном контейнеру npm-реестре пакет `@supabase/ssr` возвращает `404`, поэтому зависимости невозможно установить. Это ограничение среды проверки, а не подтверждение успешной production-сборки.

После распаковки в обычной среде с доступом к npm необходимо выполнить:

```bash
npm install
npm run typecheck
npm run build
```

## Оставшееся архитектурное ограничение

Импорт выполняется последовательностью клиентских запросов Supabase. Если связь оборвётся посередине, импорт может завершиться частично. Полная атомарность потребует отдельной серверной SQL/RPC-функции с транзакцией. Текущая версия снижает риск ожиданием всех активных сохранений, но не превращает импорт в одну транзакцию.

## Автоматический курс EUR/KZT

- Добавлен серверный маршрут `app/api/exchange-rate/route.ts`, который читает фактический курс EUR с `mig.kz`.
- Для расчётов используется курс продажи EUR.
- Клиент обновляет курс ежедневно после 08:00 по времени Алматы; если приложение открыто, запрос запускается в 08:00, если закрыто — при первом открытии после этого времени.
- При временной ошибке сохраняется последний успешный курс, повторная проверка выполняется раз в 15 минут.
- В шапку добавлен компактный информационный блок с курсом, источником и временем, опубликованным `mig.kz`.
- Курс передаётся в план Германии и автоматически сохраняется в `relocation_plans`; новая схема Supabase не требуется.


### Единая логика конвертации валют

- Удалено ручное поле курса EUR/KZT и старое единое поле `eurKzt`.
- Доходы и резерв в EUR переводятся в KZT по курсу **покупки** МиГ.
- Расходы в EUR переводятся в KZT по курсу **продажи** МиГ.
- Представление сумм KZT в EUR выполняется по курсу **продажи**.
- Старый вручную сохранённый курс больше не используется как резерв; принимаются только снимки, помеченные источником `mig.kz`.
